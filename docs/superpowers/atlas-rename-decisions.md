# The rename to ATLAS: build decisions

The rulings made while building the rename (spec: `specs/2026-10-24-atlas-rename-design.md`). Branch `atlas`, on top of `phase-4.5` (PR #7). The app was BrainHub; it is ATLAS everywhere now, except the spots listed under "What stayed".

## How it was done
- **A1 One mechanical commit, then the cut-over code.** The first commit ("rename BrainHub to ATLAS (mechanical)") is nothing but the rename script's output plus the spec. Everything written by hand comes after it, in its own commits: the voice, the hooks repair, the update step's fallback, the launcher, the web drafts, the shell's migration, the guard and the docs. So a rebase can redo the mechanical commit by script and keep the rest as patches. The mechanical commit alone fails two voice tests (`Robot arm and ATLAS.`): the next commit, `spoken_project`, makes them pass.
- **A2 The rename script lives outside the repo** (in the session's scratchpad: `rename.sh`; the lead keeps it). `rename.sh` renames every tracked file, `rename.sh FILE…` only those (the files a rebase left in conflict). It is idempotent: a second run changes nothing. It renames paths file by file with `git mv` (so a file that arrives as `app/brainhub/x.py` after a rebase lands in `app/atlas/`), applies the spec §1 replacements in order, and re-locks `uv.lock`. It reads `EVERYWHERE` and `ALLOWED` from `app/tests/test_no_old_name.py`: whole files listed there are skipped, and allowed patterns are masked before rewriting, so a re-run never rewrites the migration's own legacy names. It never touches the dev copy's path `~/dev/BrainHub`, binary files and `app/web/fonts/`, and in `Cargo.lock` only its own `name = "brainhub-desktop"` line.
- **A3 The replacement order:** the CamelCase fixtures first (below), then `BrainHub Desktop` → `ATLAS`, `Brain Hub` → `Atlas`, `BRAINHUB_` → `ATLAS_`, `brainhub-request`, `brainhub-desktop` (and GTK's `Brainhub-desktop`), `brainhub_desktop_lib`, `dev.brainhub.desktop`, `/mnt/data/BrainHub`, `D:\BrainHub` in its escapings, `%LOCALAPPDATA%\BrainHub`, `brainhub-target`, `brain-hub#N` → `#N`, `tudor-n/brain-hub` → `tudor-n/atlas`, then `BRAINHUB`, `BrainHub`, `Brainhub`, `brainhub`. Last, "a ATLAS" → "an ATLAS" (also before a backtick, as in "an `atlas-request` file").
- **A4 `productName` is just `ATLAS`** (spec §1), so "BrainHub Desktop" became "ATLAS" everywhere it named the shell ("restart ATLAS", the autostart entry `~/.config/autostart/ATLAS.desktop`).
- **A5 CamelCase test fixtures.** `spoken_project("BrainHub") == "Brain Hub"` and `("brain-hub", "brain hub")` tested the splitting at a case change and at a hyphen, so they became the owner's other CamelCase project: `("TraceGreen", "Trace Green")`, `("trace-green", "trace green")`; the docstring example too. Where "BrainHub" was a project in a merged voice line, it is now "ATLAS", spoken "Atlas" (A6).
- **A6 `spoken_project` says `ATLAS` as "Atlas"** (spec §1): a whole-word `ATLAS` becomes `Atlas` after the splitting, so "ATLAS-desktop" is "Atlas desktop". Other all-caps words are untouched (`CNC` stays `CNC`). Tested.
- **A7 History reads in the new names.** The older specs, plans and decisions are renamed too (the owner: "change the name in all the docs"), so they now say `D:\ATLAS`, `python -m atlas` and so on, even for what happened before the rename. The real files from before keep their real names where a doc points at one: `NEXT-SESSION.md` names the real backup `settings.json.brainhub-backup-20261023-113616`.

## The cut-over code (spec §2)
- **A8 The legacy names live in a few files only:** `app/atlas/legacy.py` (the Python names), `app/desktop/src-tauri/src/migrate.rs` (the shell's), `app/web/js/legacy-keys.js` (the two drafts' keys), one constant in `update_step.py` (stdlib-only, rule 15, so it can't import `legacy.py`), and their tests (`tests/test_legacy.py`, `legacy-keys.test.mjs`, `migrate.rs`'s own). `claude_integration.py`, `desktop_entry.py` and `supervisor.rs` hold no old name: they use those constants.
- **A9 `migrate.rs` beside `config.rs`, not inside it** (the spec says `config.rs`). It uses `config.rs`'s injected environment (`Env`, `os_default_dir`, `default_path_in`, `state_dir_in`) exactly as `config.rs`'s own tests do, so its tests run on temp dirs only; a separate file keeps the old names out of `config.rs` for the guard. `lib.rs` calls `migrate::run()` before reading `desktop.json` and reads the file it names.
- **A10 State first, then config.** On Linux the state folder is renamed before the config folder, so "the new `desktop.json` exists" always means "done": a failed config move leaves the legacy `desktop.json` (rewritten to name the moved state folder) where it is, and the next start finishes the move. Each move is one `rename`, only onto a missing or empty target; a non-empty target stops the migration with the legacy files untouched. If the rewrite itself fails after the state move, the shell swaps the state folder in memory (`Outcome::fix`) so it never runs on a folder that is gone.
- **A11 `migrated.json`'s `at` is unix seconds** (the shell has no date crate, and adding one for this isn't worth it).
- **A12 The sibling swap** replaces one `BrainHub` path component, the first from the left whose swapped path exists, and only for a path that is missing on disk (`root`, `live`, `app_dir`). The legacy-mode `python` isn't swapped: it lives in the dev copy, which keeps its name.
- **A13 The legacy login entry** is checked on every start without an override, not only when the folders move, so a later start finishes the job. Linux: `~/.config/autostart/BrainHub Desktop.desktop` (auto-launch's folder, always under `$HOME`), removed only when it has the line `Name=BrainHub Desktop`. Windows: `reg query` then `reg delete` of the HKCU Run value `BrainHub Desktop`, through `reg.exe` with `CREATE_NO_WINDOW` (no new crate). When one was removed, the shell turns its own autostart on during setup. The owner has autostart off, so on Kubuntu this is normally a no-op.
- **A14 The package by slot contents** (`supervisor::slot_package`, and `update_step.slot_package` for the hook copy): `atlas/` if present, else the legacy folder, else `atlas`. It picks the update step's file, the hub's `-m` and claude-sync's `-m`, in runtime and legacy mode alike. Every child that gets the state folder gets it as both `ATLAS_STATE_DIR` and `BRAINHUB_STATE_DIR`.
- **A15 Legacy hooks are "ours" everywhere.** The `_OURS` match takes the legacy suffixes `brainhub/hook_client.py` and `brainhub/hook/hook_client.py` as whole path components, so install, uninstall and status treat old entries as ours (status says installed but not current: "out of date"). `notbrainhub/hook_client.py` and `brainhub-tools/hook_client.py` stay someone else's. The CLAUDE.md block matcher takes the legacy marker pair too (a matching pair only), so install replaces it where it is and uninstall removes it. The legacy `brainhub-request` (and `.cmd`) is removed on install and uninstall only when it carries the legacy mark.
- **A16 `repair_legacy` runs before the setup check.** It is about Claude Code, not the brain, so it runs on a fresh root too, once per full start (not reduced, not read-only). It goes through `routes.repair_legacy_integration`, which passes exactly what the Settings install route passes (`app["claude_settings_path"]`, `app["port"]`, `osdirs.state_dir()`, `paths.data`), and `install` itself (backup first, atomic write, the passthrough kept from the state folder's `claude_integration.json`). A failure is a `log.warning` (to `hub.log`), never a startup error: the spec's "quiet `log_error`" is read as "logged quietly", since `app["log_error"]` is the raw log's error shown in the UI.
- **A17 No reinstall loop.** When the shell's folder move failed, the hub runs on the legacy state folder, whose stable hook copy has a legacy-looking path. `repair_legacy` then skips when the entries already run the current paths and no legacy wrapper or block is left, so it doesn't rewrite settings (with a backup) on every start.
- **A18 The trigger is the settings only** (spec §2.2): an old wrapper or CLAUDE.md block with no old hooks in the settings is left until the owner installs again.
- **A19 `desktop-entry install` removes the old launcher entry** only when it is ours (a desktop entry with the line `Icon=dev.brainhub.desktop`), and the old icon when that entry was ours or the icon is our icon's exact bytes. Its result gains `removed_legacy`.
- **A20 The drafts' legacy keys** (`brainhub.setup.v1`, `brainhub.widget.draft`) are read once when the new key is absent, copied under the new key and then removed, so the read happens once. `atlas.browse` (the Browse rail's last page) has no fallback: losing it costs one click.

## What stayed, on purpose
- **A21 The dev copy's folder `~/dev/BrainHub`** (= `/home/tudor/dev/BrainHub`): a real path, keyed by Claude Code's memory and history; the owner may rename it later. The guard allows it anywhere.
- **A22 The tablet's `bh_device` cookie and its `bh.*` keys** (`bh.queue`, `bh.draft.*`, `bh.tab`): renaming them would unpair the tablet and drop its unsent notes. Nobody sees them. Also the `bh` shorthand in `app/README.md` and the `bh-…` temp folder names in docs and tests: they are not the brand.
- **A23 The common noun "the hub"**, `hub.db`, `hub.log`, `data/` and `brain/`; the CI job names `test (ubuntu-latest)` and `test (windows-latest)` (rule 15).
- **A24 Cargo.lock's registry lines and the fonts**: only the package's own name line in `Cargo.lock` changed.
- **A25 The guard's allow-list** (`tests/test_no_old_name.py`): this doc and the spec; `legacy.py`, `migrate.rs`, `legacy-keys.js` and their tests; `update_step.py`'s `LEGACY_PACKAGE` line; in the docs, text inside "(was …)" or "(pre-rename: …)"; in `TODO.md` the owner's cut-over commands (step 8), which must name the old folders. It also fails on any tracked path containing the old name.

## Residuals
- The Windows halves (`reg.exe`, the one-folder move under `%LOCALAPPDATA%`) are compiled and tested only in CI on Windows; Windows is on hold.
- The old web view folders (`~/.local/share/dev.brainhub.desktop`, `~/.config/dev.brainhub.desktop`) are not moved: the window positions are remembered again after one start, and the owner deletes the old folders (`TODO.md` step 8).
- A pre-rename hub's held captures and integration state move with the state folder; nothing in the shared root changes name, so `hub.db`, the brain and `data/` need nothing.
