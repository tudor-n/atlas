# Dual boot: build-time rulings

Rulings made while building the dual-boot plan (`plans/2026-10-22-brainhub-dual-boot.md`) that amend or settle the plan or the design. Newest last. D1 and D2 are reserved for the two spikes the plan names.

## D1: Wayland widget spike (Task 2): run the shell under XWayland
Kubuntu 26.04, Plasma on Wayland, two screens (laptop 1536x864 logical at 125 %, external 1920x1080 at 100 %). Shell built from master's `app/desktop`, run connect-only against a temp hub. Window properties read from KWin with a script; visual checks by screenshot and by the owner.

| Check | Native Wayland (no rule) | XWayland (`GDK_BACKEND=x11`) |
|---|---|---|
| Transparent, frameless, rounded panel | (not reached) | yes |
| Stays above other windows | **no** (opened behind Firefox; `keepAbove` false) | yes (`keepAbove` true, owner confirmed) |
| Not in the taskbar | **no** | yes (`skipTaskbar`, `skipPager`) |
| Not in Alt+Tab | no | **no** (`skipSwitcher` false; owner saw it) |
| Draggable | (not reached) | yes (owner) |
| Expand/collapse resizes | (not reached) | yes (owner) |
| Position remembered | no (apps can't place windows) | yes, after a clean quit (saved 1400,750 physical = 1120,600 logical, restored exactly) |
| Kept on screen | no | yes: parked half off the bottom, it came back at y=656 (above the 48 px panel) |
| Sharp on the 125 % screen | | yes (owner) |
| Tray icon and menu | | yes (StatusNotifierItem, Active; menu items over D-Bus; owner sees it) |

**Ruling: option 1, XWayland.** It meets the parent spec §3.1 target except Alt+Tab, and needs no KWin rule. Option 2 (native plus a KWin rule) was only baseline-tested: the plan prefers option 1 when it works, and native Wayland can't restore or clamp the position by itself. Task 8 must:
- set `GDK_BACKEND=x11` before GTK starts (unless the env already sets it);
- keep the widget out of Alt+Tab: set the GTK window type hint to Utility before the window is mapped (build it hidden, set the hint, then show). If KWin still lists it, fall back to a one-line KWin rule (`skipswitcher`) installed by `desktop-config`;
- quit cleanly on SIGTERM/SIGINT (logout sends SIGTERM): call `app.exit(0)`, so the window-state plugin saves the position and the supervisor stops the hub. Today a killed shell saves nothing.
- `WEBKIT_DISABLE_DMABUF_RENDERER` wasn't needed (no blank window).
- The tray library warns that `libayatana-appindicator` is deprecated; harmless for now.
- **As built (Task 8):** the Utility type hint alone keeps the widget out of Alt+Tab (KWin only lists windows that want tab focus: normal windows and dialogs). KWin still reports `skipSwitcher` false, and that's expected. The owner confirmed it's no longer in Alt+Tab, so the KWin-rule fallback wasn't built. SIGTERM and SIGINT quit the shell cleanly and save the position (checked live). The hub runs in its own process group and shuts down within 2 s of SIGTERM (`shutdown_timeout`); the shell waits up to 10 s before killing it.
- **Still to check on the real desktop:** a real logout writes the SIGTERM line to `hub.log` (if XWayland dies first, GDK may exit without the clean path); the widget stays visible while another app is focused; on Windows, the widget built hidden and then shown behaves as before.

## D2: Claude Code memory spike (Task 11): Linux half done
Claude Code 2.1.308 on Kubuntu, a scratch project (`/tmp/bh-mem-spike`, key `-tmp-bh-mem-spike`: every non-alphanumeric character becomes `-`, case kept, a `.` too) and a scratch shared folder.
- **Option 1, a symlinked memory folder, fails on Linux.** Claude Code resolves `~/.claude/projects/<key>/memory` to its target, finds it outside the folders it may edit, and refuses to write *and* to read `MEMORY.md` ("blocked … outside the directories I'm allowed to edit"). (The design recorded an NTFS junction working on Windows with 2.1.306.)
- **Option 2, per-project `autoMemoryDirectory` in the project's `.claude/settings.local.json`, works:** the value is the memory folder itself (not a parent). The note and `MEMORY.md` were written there, and a fresh session answered from it.
- **Home sessions: `~/.claude/settings.local.json` works** (tested with the owner's OK, then removed; the real `settings.json` hash unchanged). A session started in `~` read it as its own project-local settings and wrote and read memory in the folder it names; a session in another project without its own setting didn't see that memory. No user-level `autoMemoryDirectory` is needed, so nothing leaks into new projects.
- **So Task 11 uses option 2:** `claude-sync` writes `autoMemoryDirectory` into `~/.claude/settings.local.json` (home → `memory/home`) and into each paired project's `.claude/settings.local.json` (→ `memory/projects/<name>`), merging into existing files and never touching other keys. A project with no setting yet keeps its machine-local memory until the next sync merges it into the store and adds the setting.
- **Remaining:** the Windows half (the same two checks on Windows, at the scheduled reboot).
- **As built (Task 11, `brainhub/claude_sync.py`):**
  - **Pairing** comes from the folders, never from decoding a key (the encoding loses information): the home key, the keys of the folders in the projects root (`~/dev`, `D:\`), and the folders `pairs.json` names (`{"<name>": {"linux": …, "windows": …}}`, which wins over a root folder's own name). Every other key (scratch folders, `/tmp`, the live copy on Linux) is left alone, and the hub's filing worktrees (`…-data-worktrees-e-<entry id>`, D11) are always skipped. Only the drive letter's case is folded on Windows.
  - **Merging a local folder** that stays in place: claude-sync records each merged file's hash per key in `<state>/claude-sync-last.json`, and only files new or changed since then are merged. So the backup is made once per change (not at every login), a note the owner removed from the store isn't brought back by a stale local copy, and a third differing version gets `<stem>.<os>-2.md`. `MEMORY.md` lines linking to a note kept under its second name are rewritten to that name.
  - **Skills** are copied into the store, the original is moved to `<state>/claude-sync-backups/skills/`, and the link takes its place (claude-sync never deletes a skill folder). A local skill that differs from the store's skill of the same name is left alone and reported.
  - **Settings:** a local change is timed by `settings.json`'s modification time (the only clock there is when the shell wasn't watching). On an OS's first sync, a value that differs from the store's counts as changed at that time, so the later one wins; a key missing locally isn't a removal then. `autoMemoryDirectory` is added to the default per-OS keys. The store file is `{"per_os_keys": [...], "settings": {key: {value, changed_at, deleted, os}}}`, sorted, LF. A key the owner marks per-OS is dropped from the store.
  - **Backups of `settings.json` and of `settings.local.json`** go to `<state>/claude-sync-backups/settings/`, not beside the files: the shell's watch re-runs the sync on every change, and `.brainhub-backup-*` files would pile up in `~/.claude` and in project folders.
  - A project's `.claude/settings.local.json` is added to its `.git/info/exclude` when git doesn't ignore it yet (an untracked file would make the live copy look dirty to the update step).
  - The store counts as available only with its `memory/` folder and a successful write probe; `claude-sync init --shared <dir>` (by hand, with the owner) is the only thing that creates it. The shell's settings watch runs `claude-sync --settings-only` (settings and the commit).

## D3: Legacy integration files are adopted only by install/uninstall (Task 3)
The plan had the integration view (`GET /api/integration`) adopt the legacy Windows files from `data/` too. But moving `statusline_passthrough.txt` on a GET cuts an installed status line off from it: `settings.json` still names `D:/BrainHub/data/statusline_passthrough.txt` until a reinstall, so the owner's own line would quietly stop showing. Only install and uninstall adopt, and both rewrite the status line in the same step. The rollout reinstalls the integration on Windows anyway.

## D4: Windows boot id from the registry boot counter (Task 3, amends P11)
Review found that the boot time rounded to the minute can differ between two processes of one boot (the wall clock drifts against `GetTickCount64` near a minute edge), which would let the hub lock be taken over from a live hub. The boot id now comes from Windows' own boot counter (`PrefetchParameters\BootId`, a DWORD bumped every boot), read-only via `winreg`. The rounded boot minute stays only as a fallback if the value can't be read.

## D5: The root guard needs positive evidence (Task 5 review)
- **A marker without `brain/map.json` is "foreign"**, not ok: the brain went missing. As ok, the full app would run over it, and confirming a proposal would write a new near-empty `map.json` (the anti-goal). Setup never runs there; the banner says to restore `brain/` (Task 6 holds captures meanwhile).
- **Errors are never "absent".** On Python 3.14 `Path.exists()` is False on any `OSError`, so an unreadable or I/O-failing root looked fresh. The guard uses strict `os.stat` checks (only "no such file" means absent), and any `OSError` while classifying gives "missing".
- **The hub lock records the holder's process start time** (`pid_start`: Linux `/proc/<pid>/stat` field 22, Windows `GetProcessTimes`). The shell kills the hub, so stale locks are normal, and a reused pid used to look like a live hub, blocking every start. A lock naming our own pid is stale too.
- `usage.json` and `settings.json` writes create `data/` but never its parents, so a root that vanished mid-run is never recreated.

## D6: Time zone check compares real UTC offsets (amends P5)
`time.altzone` is always `timezone - 3600` on Windows' CPython, even for zones without summer time, so comparing `timezone`/`altzone` across OSes could warn falsely. The marker stores the UTC offsets at noon on 15 January and 15 July (`tm_gmtoff`), and each start compares its own.

## D7: Brain git on two OSes: case rule per OS, filing path guard details (Task 7)
- **Every brain git call sets `core.ignorecase` for the OS running it** (`false` on POSIX, `true` on Windows) with `-c`, whatever the shared `.git/config` says, which is never edited. With Windows' `true`, Linux git didn't see an agent's `robot.md` next to `Robot.md` (the filing dropped it quietly), and the owner-edits sweep committed a case-only rename made on Windows as a deletion (which the backup then pushed). A brain first made on Linux has no `ignorecase`, so Windows git would compare case on NTFS.
- The case-clash check also compares folder names, and folds case as NTFS does (per-character uppercase), not `str.lower()`.
- Reserved names: CON, PRN, AUX, NUL, CONIN$, CONOUT$, COM0-9, LPT0-9 and COM/LPT with a superscript digit, with any extension, in any case.
- Agent rows refresh `os` and `boot` on every event, so a session resumed after a hub restart in the same boot isn't ended as a ghost.
- Leftover worktrees are removed with `worktree remove --force --force`: a power cut during `worktree add` leaves one locked, and a single `--force` (or prune) skips it on every retry.
- The status-line passthrough runs in its own process group (`process_group=0`) but not a new session, so the owner's command keeps the controlling terminal.

## D8: Reduced mode and read-only root, as built (Task 6)
- **`run_server` serves the reduced app; `create_app` still raises `RootUnavailable`.** It raises for missing, foreign and newer roots, and for a read-only root whose `hub.db` can't be read read-only (absent, damaged, or at an older schema that would need a migration). A locked or unopenable `hub.db` on a writable root is not damage: the start stops with a message, nothing is moved, and the shell retries.
- **No re-check while "newer".** Newer data never turns older while this code runs, and with a newer `hub.db` the root itself checks ok, so a watch would restart the hub every 15 s. An update restarts the hub anyway.
- **The watch is `check_root` as is.** A legacy brain (map, no marker) coming back gets its marker from it: the only write, and only to a root that is about to run in full.
- **`POST /api/open` works in every mode.** It writes nothing, and the widget's "Open in BrainHub" stays usable.
- **The read-only view is the last checkpoint.** `immutable=1` doesn't read a `-wal` left by a crash, so the newest index changes can be missing until the next full start. The raw log is untouched either way.
- **Held captures are marked queued when flushed**, as a fresh capture is, so the cap on never-filed entries at start (`MAX_AUTO_REQUEUE`) doesn't turn them into failures.
- **`port_free` binds with `SO_REUSEADDR` on POSIX**, as aiohttp does. Without it the restart right after exit 75 was refused for a minute (the old hub's connections in TIME_WAIT).
- **Manual check** (Kubuntu, temp roots, temp state folder, `claude_path` pointed at a missing command): a missing root showed the banner, held a capture (200), answered Today with 503 and a hook with 204, and was never created. Once a brain appeared there the hub exited 75 after 15 s; the restart put the held capture in its own day's file and queued it. A read-only root (`chmod -R a-w`) served Today and the journal, refused confirm (503), held a capture, and left `hub.db` unchanged with no `-wal`/`-shm`; after `chmod -R u+w` it exited 75 after 15 s and the restart flushed the capture.

## D8 addendum (Task 6 review)
- **Held captures belong to a root.** Each record stores `root: {id, path}`: the marker id when the marker is readable at hold time, and the resolved root path (all there is for a missing or fresh root). A start flushes only the records held for its own root. When both sides have a marker id the ids decide, so the same drive mounted at another path still matches and a new brain set up at the old path doesn't; otherwise the paths decide (case-folded on Windows). The others stay held, with one line in `startup_errors`, and the banner's held count is per root too. Before, a dev hub on a temp root without `BRAINHUB_STATE_DIR` would pull the real held captures into a throwaway brain. A record without `root` (none exist yet) matches any root.
- **The Fast Startup watch keys on hibernation** (amends the plan's two values): `HibernateEnabled` == 1, or `HibernateEnabledDefault` == 1 when `HibernateEnabled` isn't set. `powercfg /h off` turns hibernation off, and Fast Startup can't run without it, but `HiberbootEnabled` can stay 1: a warning keyed on it would never go away once the owner followed it.
- **The raw log never recreates a vanished brain.** `append_entry` raises `OSError` unless `brain/` is an existing folder, and creates only `log/YYYY/MM` below it. A capture whose append fails with `OSError` mid-run (the drive went read-only or away) is held on this OS and answered 200 "saved, held"; on a root that was ok at start, a missing `map.json` no longer answers 409 "run setup first". If part of the record reached the file before the error, the held copy (a new id) duplicates it at the flush: a duplicate beats a loss.
- **Read-only UI: confirm and tick are disabled with the reason**, as the spec says: the card's ✓ and "Confirm all", and the Today ✓, with the drive message as their title. Today reads `drive` from `/api/state` on each refresh. Every other write (dismiss, edit, snooze, correct, retry) still answers 503 with the reason, shown inline.

## D9: The update step runs only CI-checked master, and never overwrites the owner's data (Task 9 review, amends P9)
- **Provenance guard.** The refresh builds a slot only from a live HEAD on branch `master` that equals, or is an ancestor of, the local `refs/remotes/origin/master`. Otherwise the old slot stays and `pending` says why, in the pull's words when the pull skipped for the same reason (one note, not two). It needs no network, so an offline start still builds what the other OS pulled; a dirty tree still builds (the archive is of the commit). `runtime init` checks the same before touching anything and exits 1 with a message. A commit made in the live copy, or another branch checked out there, never runs.
- **`merge --ff-only --no-autostash --no-overwrite-ignore`.** Without the last flag, git 2.53 quietly replaces an ignored file that the new commit tracks, and the live copy's `brain/` and `data/` are ignored and hold the real data. Now git refuses, and the step reports "fast-forward failed" with git's stderr.
- **The gate waits on every check run** (amends P9). Any run not `completed` → "CI pending"; any completed run whose conclusion isn't `success`, `skipped` or `neutral` → "CI failed" (this catches `startup_failure` and `stale`); `total_count` above the runs listed → unreadable. Both `test (…)` jobs must have succeeded. The request is `GET …/check-runs` with `per_page=100` and `filter=latest` passed as `-f` fields: the same query string, with no `&` on a command line that a `.cmd` shim would split.
- **Budget.** `--budget` (75 s, inside the shell's 90 s) caps the whole step. Each call gets the smaller of its own cap and the time left: network calls `--timeout` (now 20 s), local git 60 s, the venv sync only the budget. A fast-forward with under 15 s left, or a venv sync with under 30 s, is put off ("… put off (not enough time)"), so the budget never kills git halfway through updating the live copy. A timeout kills the whole tree (own session and `killpg` on POSIX, `taskkill /T /F` on Windows).
- **Lock.** The step and `runtime init` take `<state>/runtime/update.lock` without waiting (`flock` on POSIX, `msvcrt.locking` on byte 0 on Windows). The OS drops it when the holder dies, so it never goes stale. If it's busy: "update already running", and nothing is touched. Temp files carry the pid. A slot is current only while its `slot.json` names `current.json`'s commit, so a wiped or half-built slot never is.
- **Kept from the build:** the gate reads `git config --get remote.origin.url`, not `get-url`, so an `insteadOf` rewrite can't change which repo it asks about; the merge is of the exact sha CI checked, not `origin/master`; `GIT_DIR`-style env vars are stripped from every child; the hook copy is compared, and put right, on every run, not only after a flip.
- Also: `update.json` gains `stderr`, the last failed call's stderr tail (≤ 500 characters, URL credentials masked), when something is pending. `deps` covers `app/.python-version`. uv is also looked for in `~/.local/bin` (as P6 does for claude). `shell_source` adds `build.rs`, `tauri.conf.json` and `capabilities/**` (the algorithm is in its docstring, and `test_shell_source_algorithm` pins a digest for the Rust side).
- Every git call on the live copy passes `-c gc.auto=0 -c maintenance.auto=false`: a background gc started by fetch or merge detaches itself, outlives the budget's kill and would keep writing to the shared drive.

## D10: Claude Code integration on Linux and across runtime slots (Task 10)
- **Runtime mode needs both files.** `hook_paths()` uses the stable paths only when `<state>/runtime/current.json` *and* `<state>/hook/hook_client.py` exist, so it never writes a script path that isn't there yet; otherwise the dev paths, as before.
- **The base interpreter is never resolved.** It is `sys._base_executable` through `console_python`. With uv on Linux that is `~/.local/share/uv/python/cpython-3.14-linux-x86_64-gnu/bin/python3.14`: uv's minor-version link, which a patch upgrade re-points, while resolving it would pin a patch folder that an upgrade can remove. A missing base falls back to `sys.executable`. A Python minor bump (`.python-version`) re-syncs the slot venv, and the hooks keep the old interpreter, still installed, until the next install.
- **The Linux status line is `shlex.join`** of its words (`sh` runs it), with no slash conversion: a backslash is part of a POSIX name. Windows keeps the phase 2 form.
- **Ours = whole path components.** A hook or status line is ours when it names `…/brainhub/hook_client.py` (the package's copy), `…/brainhub/hook/hook_client.py` (a default state folder's stable copy, any case, either OS), or exactly the stable copy of the state folder in use (any name, e.g. under `BRAINHUB_STATE_DIR`; bare, double-quoted or `sh`-quoted). `status()` takes that state folder (default: this OS's). Before, any text containing `brainhub/hook_client.py` counted, `notbrainhub/hook_client.py` included.
- **Measured on Kubuntu with Claude Code 2.1.308** (`app/README.md` → Measured → Phase dual-boot):
  - exec-form hooks (`command` + `args`) work on Linux, with the base interpreter and the stable copy;
  - `CLAUDE_CODE_ENTRYPOINT` is `sdk-cli` under `claude -p`, as on Windows;
  - hooks fire even when not logged in (SessionStart, UserPromptSubmit, SessionEnd);
  - the status line doesn't run under `-p`.
- **`WHERE_BY_ENTRYPOINT` is unchanged.** The terminal and VS Code values weren't measured. An interactive session can't run against a scratch `CLAUDE_CONFIG_DIR` (no login), and with the real one it would write `~/.claude/projects/**`. The owner checks them at rollout (plan Task 10, "Linux entrypoints"); `cli` is expected for the terminal.
- **An e2e on the real login leaves a folder behind:** even with `--no-session-persistence`, `claude -p` creates an empty `~/.claude/projects/<key of the cwd>/memory/`. Remove it afterwards.

## D11: The hub's own Claude runs have no auto memory (Task 10 review)
Measured with Claude Code 2.1.308: with the runner's isolation flags (`--setting-sources ""`, `--no-session-persistence` and the rest), `claude -p` still gets auto memory. Its instructions name `~/.claude/projects/<key>/memory/` for its cwd, and the folder is created. So every filing (cwd `data/worktrees/<entry id>`) left a stray folder in the owner's `~/.claude/projects` (on Windows since phase 2), and the filing agent, which may write files, was told about a folder outside its worktree. `child_env()` now sets `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` (measured: no path in the instructions, no folder). Stray `*-data-worktrees-e-*` keys left by earlier runs are cleaned up at the rollout, and `claude-sync` must never pair them as projects.

## Residuals
- An integration installed before `runtime init` keeps the dev paths (the dev venv and the dev copy's `hook_client.py`). Status still shows it as installed; reinstall after `runtime init` (the rollout installs it after).
- claude-sync: a project folder on `D:` that sessions on both OSes start in has one `.claude/settings.local.json`, holding the path of the OS that paired it. Windows pairs `D:\BrainHub` (the live copy) as `BrainHub`, so a Kubuntu session started in `/mnt/data/BrainHub` would read a Windows path for `autoMemoryDirectory`. Kubuntu sessions work in `~/dev/BrainHub` (its own file), so it doesn't arise in the intended setup; a `pairs.json` entry naming one folder for both OSes would make it flip at each sync.
- claude-sync's Windows cases (junctions, drive-letter keys, `D:\` defaults) are tests skipped on Linux; they first run in CI on `windows-latest`, and for real at the D2 Windows half.
- `app/README.md` still says the integration files live in `data/` (Task 12 fixes the docs).
- `map.json` load/change/save isn't serialised across `PUT /api/map`, the Reviewer's `add_node` and the Agents link: two edits at the same moment could lose one (the first two already raced before the dual boot).
- `//server/share` counts as a Linux path (P7 to the letter), so the map editor on Windows calls it a Linux folder; UNC paths in the `\\server\share` form are fine.
- Two hubs started at the same instant on one root can both take the lock; the port check and the supervisor make this unlikely in practice.
- `app["root_status"]` stays "fresh" after setup on the started app (aiohttp freezes it); "fresh" and "ok" show no banner alike, so nothing reads the difference.
