# Phase 2 build decisions

These are the decisions taken during the autonomous build of phase 2 (2026-10-21) where the plan or the phase 2 design was silent, wrong, or in conflict with what was measured. Each one says why it was made and what it costs if wrong. The parent spec (`specs/2026-10-20-brainhub-design.md`) stays the authority; the phase 2 design (`specs/2026-10-21-brainhub-phase2-design.md`) makes it concrete, and these rulings amend that design where they disagree.

## Rulings
- Ruling 1 (T4): The broadcast tests record events by replacing `app["broadcast"]` with a recorder before the test client is created (routes read `app["broadcast"]` at call time). — Why: the plan's test text was non-committal about how to observe broadcasts. — Cost if wrong: the tests get rewritten.
- Ruling 2 (T6): The installer writes the **console** interpreter into the hooks and status line: if `sys.executable` is `pythonw.exe`, the sibling `python.exe` is used (`claude_integration.console_python`). — Why: design §4.2 says `sys.executable`, but under the desktop supervisor the hub runs as `pythonw`, and hooks need stdin while the status line needs stdout; with `pythonw` the status line would print nothing. — Cost if wrong: none (`python.exe` always exists in a venv).
- Ruling 3 (T2): An unchanged usage payload refreshes `updated_at` in memory only; `data/usage.json` is written only when a value changes. — Why: the status line runs every few hundred ms during a session; a file write per tick is waste. — Cost if wrong: after a hub restart, the age shown is from the last change, slightly older than reality.
- Ruling 4 (T5): The hook client uses a 0.25 s **connect** timeout plus a 1.0 s (event) / 0.5 s (status line) budget for send and response, so a downed hub costs about 0.3 s per hook. — Why: design §4.2 assumed a refused localhost connect fails instantly; on Windows it is retried for about 1.1 s, which a 1 s timeout would have paid on every hook. — Cost if wrong: an event is lost if a loaded machine takes more than 250 ms to accept a localhost connection.
- Ruling 5 (T6, carried from T5): `UserPromptSubmit`, `Notification` and `PostToolUse` hooks are `async` (they never make the owner wait on typing or tool flow); `SessionStart`, `Stop`, `StopFailure` and `SessionEnd` stay synchronous so they are not cancelled at teardown. — Why: refines design §4.2, which made only `PostToolUse` async. — Cost if wrong: async events may arrive slightly out of order (a brief running/waiting flicker).
- Ruling 6 (T6): Ownership in the owner's settings is **per hook**, not per matcher group: uninstall and re-install filter our hooks out of each group and drop a group only if it ends up empty. Ours are recognised by the path suffix `brainhub/hook_client.py` (separators normalised, case-insensitive), in `args` for hooks and in `command` for the status line. — Why: supersedes design §4.2 ("a group whose single hook…") and a generic `hook_client.py` marker; owner-defined hooks and status lines must never be lost. — Cost if wrong: an entry installed from a renamed package folder isn't recognised and has to be removed by hand.
- Ruling 7 (T7): `/api/widget` `projects[].open` counts all open items, including next-time notes; `next_time` is a subset of it. The tile caption is "with open items". — Why: the design was silent on whether next-time notes count as open. — Cost if wrong: a project with only next-time notes counts as having open items.
- Ruling 8 (T8): The usage "resets" text prefixes the date (`MM-DD`) when the reset is not today. — Why: the weekly window resets days away, so the brief's exact `resets 14:20` would be wrong for it. — Cost if wrong: slightly longer text.
- Ruling 9 (T9): The widget's `fitWindow` measures the panel's bounding height, not `document.documentElement.scrollHeight`. — Why: `scrollHeight` never drops below the viewport, so collapsing would never shrink the Tauri window; amends the brief's interface text. — Cost if wrong: none.
- Ruling 10 (T9): The widget's Usage tile falls back to the `seven_day` window, labelled as weekly, when `five_hour` has no value. — Why: the design was silent; an empty tile while the weekly figure is known is less useful. — Cost if wrong: the tile shows the weekly % (labelled as such).
- Ruling 11 (T9): `data-tauri-drag-region` goes on the widget bar **and** its grip, dot and synopsis children. — Why: Tauri v2 checks the event target, so the attribute on `.bar` alone (as the brief had it) doesn't drag when the press lands on a child. — Cost if wrong: none.
- Ruling 12 (T10): A hard-killed or crashed desktop shell leaves the hub it started running (no Windows job object). The next shell launch finds the port answering and adopts that hub as external. — Why: the hub is the thing that must keep running; the shell is only its frame. — Cost if wrong: an orphan hub after a shell crash until logoff, and "Restart hub" is greyed out for it.

Fix wave after the final whole-branch review (2026-10-21):
- Ruling 13 (amends design §8 "pythonw"): `desktop-config` writes the **console** `python.exe` (`claude_integration.console_python(sys.executable)`), and the supervisor keeps `CREATE_NO_WINDOW`. That flag gives the hub a hidden console, which every git, claude and taskkill process it starts inherits. As belt and braces, `gitrepo.py` and `claude_runner.py` also start their children with `CREATE_NO_WINDOW` on Windows. — Why: `pythonw.exe` has no console, so `CREATE_NO_WINDOW` on it was moot, and each console child of the hub (every commit, filing and kill) opened a new visible console window; a probe and the re-check confirmed no window with `python.exe`. — Cost if wrong: none seen; `hub.log` still gets stdout/stderr through the supervisor's file handles.
- Ruling 14: The shell navigates the widget window to the hub's `/widget` **once** (`needs_navigate` in `lib.rs`: the port answers and the window isn't already on that URL). After that a hub restart doesn't reload the page; the page rides it out (offline text, 5 s retry, WebSocket reconnect). The widget also keeps the capture text as a draft in `localStorage` (`brainhub.widget.draft`; saved on input, restored on load with the widget expanded, cleared after a successful save; every storage access in try/catch). — Why: the old re-navigation on every down→up reloaded the page and dropped unsaved typed text, against the anti-goal "never silently drop what the owner wrote". — Cost if wrong: if the first navigation lands on an error page with the hub's URL, the window stays there until the shell restarts; a draft stays in WebView2 storage until saved or cleared.
- Ruling 15: The hub uses the port it is **bound** to: `run_server` stores it in `app["port"]` (`create_app` defaults it to the settings port), and `/api/open` and the integration install/status use it. The supervisor passes `--port <desktop.json port>`. The Settings hint says to restart, install the integration again, re-run `desktop-config` and restart BrainHub Desktop. — Why: after a port change the shell polled the old port while its child listened on the new one (and was never respawned), "Open BrainHub" went to a dead port, and Install wrote a port the hub wasn't on. — Cost if wrong: after a port change a shell-started hub stays on the old port until `desktop-config` is re-run and the shell restarted (by design: consistent rather than split).
- Ruling 16: The widget window is clamped into its monitor's work area (physical pixels, `current_monitor()` then the primary monitor) once after it is built and on every `Resized`: if it sticks out at the bottom it moves up to `max(top, bottom − height)`, and likewise horizontally. — Why: expanding grew the widget off the bottom of the screen (seen in the e2e at y = 1021 px). — Cost if wrong: dragging is not clamped, so a window dragged partly off-screen stays there until its next resize.
- Ruling 17: A session that has ended (`ended_at` set, still lingering) is shown as **ended**: `/api/agents` rows carry `ended: true` and sort last, the Agents page labels them "ended" and mutes them, and `/api/widget` excludes them from the running/waiting/finished/idle counts (so from the synopsis and attention) and reports their status as `ended` in its rows. The stored status is unchanged. — Why: a session closed mid-turn kept showing (and counting) as running or waiting for the whole linger. — Cost if wrong: none; the row still disappears after `agents_end_linger_s`.
- Ruling 18: `ArmProbe` caches a negative result for 60 s (`neg_ttl`) and a positive one for 15 s (`ttl`). — Why: the arm is normally offline, and a refused localhost connect costs about 1 s on Windows, paid on `/api/widget` every 15 s. — Cost if wrong: the Robot arm tile can say "offline" for up to 60 s after the arm server comes up.
- Ruling 19: `run_server` test-binds `127.0.0.1:<port>` (bind, then close) before `create_app`, and exits with `BrainHub: port N on 127.0.0.1 is already in use (is another hub running?). Not starting.` if it is taken. — Why: a hand-started second hub on the same root ran its startup work (log scan, git sync, filing recovery) before failing to bind. — Cost if wrong: aiohttp runs `on_startup` before it binds, so the window between the check and the real bind is this hub's whole startup. Two hubs started within seconds of each other can both pass the check and both run startup work; the second still fails loudly at its own bind. The check does stop the common case, a hub that is already up.
- Also in the fix wave (no ruling needed): the widget tile caption no longer clips descenders (`.tile { height: auto; min-height: 64px }`, `.tile .caption { flex: none }`), and `usage.py` accepts an integral float `resets_at` (`1800003600.0`, stored as an int).

Owner feedback from the Linux test drive (fixed 2026-10-23):
- Ruling 20 (amends design §6's per-window merge): within one window, the usage store keeps the **highest** `used_percentage`. A later window replaces it; an earlier one is ignored. A stale reading doesn't refresh `updated_at`. Readings whose `resets_at` are less than an hour apart (`SAME_WINDOW_S`) are one window, because a new window only starts after the old one ends; so the status line and the hub's runs may disagree by a second. Readings are rounded to 2 decimals, so `0.29 × 100` equals 29. — Why: every running Claude Code session posts its own last response's numbers, so an older, lower reading overwrote a newer one and the meter read about 2 points low. Usage only rises inside a window. — Cost if wrong: if usage is ever lowered inside a window that keeps its `resets_at`, the meter stays high until that window ends.
- Ruling 21: The hub's own `claude -p` runs feed the meter. Each run's `rate_limit_event` (`rate_limit_info.unifiedWindows.<window>.utilization`, a 0–1 fraction, claude 2.1.309) goes through the same store as a status line post (`usage.rate_limits_from_event`, `routes.record_usage`), except on a read-only root. For that, schema runs (filing) moved from `--output-format json` to `stream-json --verbose` (no partial messages): the last `result` line is the same object, `structured_output` included. Events are read as they arrive, so a run that fails or times out still reports its usage. Recording runs as a background task (`app["background"]`), so an fsync or a slow page never holds up an answer or a filing. Settings' "Last usage update" stays the status line's own clock (`app["statusline_seen"]`, memory only), so it still tells whether the integration posts. A utilization over 1 shows as 100 %. — Why: filings and answers use the plan too, and no status line reports them; with no Claude Code session open, the meter never moved. Review fixes: only `\n` ends a stream line (the CLI leaves U+2028, U+2029 and U+0085 raw; `str.splitlines()` cut such a result line apart and failed the filing), and a nonzero exit names the CLI's own error from its result event as well as the stderr tail. — Cost if wrong: the event is undocumented. If its shape changes, runs stop feeding the meter (the parse ignores what it doesn't know) and the status line still does.
- Ruling 22: The hub's own `claude` runs set `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1` (`child_env()`). — Why: measured with 2.1.309, start-up fell from 0.5–0.9 s to 0.2 s, and the wait for the CLI to exit after its `result` line from 0.7–0.9 s to 0.02 s. That makes each filing and answer about 1.2–1.6 s faster with no process handling, where ending a run at its `result` line would have meant leaving a CLI (perhaps mid-write of `~/.claude.json`) to finish on its own, or killing it. Its `rate_limit_event` still comes. — Cost if wrong: these headless runs send no telemetry or error reports and never trigger a CLI update; the owner's own sessions are untouched.
- Ruling 23: Filing shows live progress. `run_json(on_step=…)` reports each `tool_use` in a finished assistant message. The worker turns it into a short label (`filing.step_label`: "reading projects/robotarm/notes.md", "looking for general/**", "wrapping up" for `StructuredOutput`, "working" for anything else, at most 80 characters, paths relative to the worktree), keeps the latest in memory (`FilingWorker.progress[entry_id] = {started, step}`, gone when the filing ends) and broadcasts `filing.progress`. `GET /api/filings/<id>` carries `progress`. The card shows "Filing… <step> · N s" (only the step is announced; the seconds tick, `aria-hidden`), and "Waiting to be filed…" while queued. The capture tray opens an entry's card **as soon as it is saved** (it used to appear only once filed, behind a static "Saved · filing…"); a capture held while the drive is missing still gets its card once filed. — Why: the owner found filing slow, and the card showed a static "Filing…" for 10–20 s. The model's time can't be cut much (Haiku was no faster and filed worse), but the wait can be visible. — Cost if wrong: the step shows the last tool call, so a long think after it ("writing general/andrei.md · 15 s") still names that call; a step update is one more WebSocket message per tool call.

## Design-time calls (marked "my call" in the design, kept as built)
- `Notification` `idle_prompt` makes a row `waiting` only if it was `running` (a missed Stop); a `finished` row stays `finished`. idle_prompt fires about 60 s after every finished turn, so following parent spec §11 literally would turn every finished row amber a minute later.
- `StopFailure` maps to `waiting` with the error type as the note: the turn died, so the owner must act.
- Events whose `entrypoint` starts with `sdk-` (`claude -p` and SDK runs) never create rows, and neither do events whose `cwd` is inside the hub's `data/` or `brain/`.
- Command hooks in exec form only, no `type: "http"` hooks: an HTTP hook to a downed hub printed `SessionEnd hook [...] failed` in the owner's terminal (parent spec §7.2 forbids visible errors), and HTTP hooks did not fire on SessionStart.

## Facts learned in the e2e (2026-10-21, Claude Code 2.1.306)
- Claude Code **sets `CLAUDE_CODE_ENTRYPOINT` itself** for hook processes: under `claude -p` hooks see `sdk-cli` even when the parent environment says `cli`. An e2e that wants rows must force the variable inside the hook command (a copy of the installed settings with each hook wrapped as `cmd.exe /c "set CLAUDE_CODE_ENTRYPOINT=cli&& <python> -I -S <hook_client.py> event --port P"`).
- Under `-p`, the async `UserPromptSubmit` hook was delivered, as were the synchronous `SessionStart`, `Stop` and `SessionEnd`.
- The desktop exe puts its WebView2 data in the real `%LOCALAPPDATA%\dev.brainhub.desktop` even when `LOCALAPPDATA` is overridden (Tauri resolves known folders, not the env var), so a manual run leaves that folder behind. `desktop.json` itself does follow the env var.

## Known residuals (deferred minors that still apply)
None of these loses owner data; most are test gaps or rare paths.

**Config and usage**
- The `fable_usage_url` and `arm_url` regexes use `re.match` with `$`, so a value with a trailing newline passes validation. `/api/open` re-validates with `fullmatch` before opening, so nothing malformed is ever opened.
- `data/usage.json`: an unparsable `updated_at` discards the whole file on load, and `updated_at` isn't range-checked (an absurd value could raise `OverflowError`, uncaught in `_load`). Only the hub writes the file.
- Test gaps: no test that `usage.changed` is broadcast on a change but not on an identical repeat; URL and limit tests are thin (paths in URLs, bare `https://`, spaces, warn 1/100, invalid stored `widget_tiles` fallback).

**Agents**
- Ignorable events (an unknown Notification type, `idle_prompt` on a finished row) still rewrite the row and bump `last_event_at`, which affects ordering.
- Activity after `SessionEnd` (other than a new `SessionStart`) leaves `ended_at` set, so the row shows as ended (Ruling 17) and is pruned after the linger even if it is running.
- `datetime.fromisoformat` on stored strings in `rows()`/`prune()`, and `int()` on the linger/stale settings, could raise on a corrupt value.
- `DELETE /api/agents/{id}` broadcasts `agents.changed` even for an unknown id; the 30 s prune interval is a literal, not a constant.
- Test gaps: `norm_path`/`is_within` directly, absolute `gitdir:`, a broken `gitdir:`, the linger boundary, the Store agent round-trip, PATCH/DELETE broadcasts, no broadcast for ignored events, the prune task.

**Hook client**
- The request budgets are per socket operation, not a total deadline. The status line's worst case (hub hanging, then a slow passthrough) is about 0.75 + 2 s, and up to about 4.5 s if `taskkill` stalls; if `taskkill` fails, closing the pipe could block behind the reader.
- The passthrough command's output is decoded as UTF-8, not the console's OEM code page.
- Test gaps: status line with the hub down, non-dict `rate_limits`, garbage stdin; `free_port()` has a bind race.

**Installer**
- An unreadable `data/claude_integration.json` on re-install loses the saved previous status line; a saved previous status line is restored on uninstall even if the owner removed `statusLine` by hand meanwhile.
- Backups (`settings.json.brainhub-backup-*`) are never pruned.
- `status` is approximate (a partial install shows as installed; "previous status line" is inferred from `--passthrough-file`).
- The temp file name is fixed and there is no lock, so two concurrent installs could collide.
- The CLI translates `IntegrationError` but not `OSError` (a locked file prints a traceback).
- The ownership match is a substring test, so a path like `mybrainhub/hook_client.py` would also count as ours; the `MARK` constant is unused; an original `"hooks": {}` is dropped rather than restored exactly.

**Widget, UI and API**
- `/api/open`: an `OSError` from the opener becomes a generic 500. Untested: the 1 s arm probe timeout and usage-warn driving `attention`; the probe test rebinds a just-closed port (possible Windows flake). `compute_today` is fed dummy lists in one test; the synopsis in `widget.py` relies on `resets_at[-5:]` being `HH:MM`.
- Usage view: a redraw wipes a "Couldn't open it" error. Agents view: `patch()` resets the dirty flag; `del()` sends a `{}` body; a forced redraw after a blur-PATCH can wipe a different row's freshly focused editor (millisecond window); Enter/Esc/delete flows have no automated test.
- Widget: tile width is an implicit `1fr`; collapsing doesn't clear the capture status; "Loading…" stays on a slow first fetch; the `openInApp` error path re-renders the popup without restoring focus; a `render()` exception skips a queued re-run.
- The capture draft lives in `localStorage` for the origin `127.0.0.1:<port>`, so after a port change an unsaved draft stays behind with the old origin. The draft-wiring in `widget.js` (input → save, load → restore and expand) is verified by hand (CDP in the fix-wave re-check), not by an automated test; the storage helpers are unit-tested.

**Desktop shell**
- The shell reads `desktop.json` only at start: after `desktop-config` is re-run, the shell must be restarted (documented in both READMEs and the Settings hint).
- The supervisor lock is held during the port check (the tray can block for about 0.5 s); `restart()` doesn't wait for the port; `desktop-config` doesn't warn when `--root` isn't a hub root; `<root>/data/hub.log` grows without bound.
- Rust tests: the spawn test checks stopping weakly, the tick invariant (child vs `started_at`) isn't asserted, and the tests leave temp files.
- Seen in the e2e: on first launch (1920×1080 at 125 %) the window appeared at the bottom edge (y = 1021 px) rather than centred. Why it wasn't centred is still not investigated; the work-area clamp (Ruling 16) now pulls it back on screen at start and on every resize, but not while it is dragged.
- The `navigate once` and clamp logic is unit-tested as pure functions (`needs_navigate`, `clamp_into_work_area`); the Tauri wiring around them was checked by hand in the fix-wave re-check.
- The venv's `python.exe` is a launcher that starts the real interpreter as its child; the supervisor kills the launcher (as it did with `pythonw`), and the interpreter goes with it.

**Parked after the final re-review (2026-10-21)**
- Navigating to the widget happens once (Ruling 14). If the hub accepts the TCP connection and then dies before the page loads, the window can stay on WebView2's "can't reach this page" until the shell restarts. Fix later: re-navigate when the page never finished loading.
- `keep_on_screen` runs on every `Resized`, including the one a minimise sends, when the window sits at (-32000, -32000). Add an `is_minimized()` / zero-size guard if Win+D or Win+M ever leaves a stray caption.
- `port_free` binds without `SO_REUSEADDR`. On POSIX, a quick restart could be refused while the socket is in TIME_WAIT. Windows, the target, is not affected.
- With `CREATE_NO_WINDOW`, Ctrl+C in a hand-run hub terminal no longer reaches the `claude` and `git` children directly. They still stop through the hub's own shutdown, but the tool subprocesses of a running `claude` may outlive it.
- `python -m brainhub integration install` (the CLI) writes the settings port, while the in-app Install writes the port the hub is bound to. After a port change, restart the hub before reinstalling from the CLI.
- The widget popup's meta line shows raw status words (`running`, `ended`) instead of the Agents page labels.
- Whether window-state restores the position before the first clamp is not verified. The first `setSize` from the page triggers a clamp anyway.
